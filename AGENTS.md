# QWEN.md — Project Context for iromu/recipe-registry

## Directory Overview

This is a **personal recipe registry** for [sparkrun](https://github.com/spark-arena/sparkrun), a CLI tool that runs optimized inference recipes on NVIDIA DGX Spark hardware. The registry contains declarative recipe definitions (.yaml), launcher scripts (.sh), and benchmark results (.json, .md) for running various large language models with different quantization schemes and backends.

The primary target hardware is the **DGX Spark (NVIDIA GB10, 128 GB unified memory, sm_121a)**. Recipes are designed to maximize throughput on this specific device.

## Key Concepts

### Recipe Format (v2)

Each recipe is a **pair** of files: a `.yaml` definition and a `.sh` launcher script.

**YAML structure** (`recipes/<model>/<name>.yaml`):
- `recipe_version`: Always `"2"`
- `model`: HuggingFace model ID (e.g., `nvidia/Qwen3.6-35B-A3B-NVFP4`)
- `runtime`: Inference engine — `vllm`, `llama-cpp`, or other backends
- `container`: Optional Docker image to use
- `metadata`: Human-readable description, benchmark results, model params, HF links
- `defaults`: Default configuration values (port, host, tp/pp, GPU memory, context length, etc.)
- `env`: Environment variables injected at runtime
- `command`: The actual inference server command with `{variables}` templating

**Shell script** (`recipes/<model>/<name>.sh`):
- Typically just calls `uvx sparkrun run <recipe-name>`
- May include stop-before-run logic (e.g., `sparkrun stop` then `sparkrun run`)

### Benchmark Files

Three categories of benchmark output, all auto-generated by `bench.sh` and friends:

| Prefix | Tool | Format | Content |
|--------|------|--------|---------|
| `benchy_` | `llama-benchy` | JSON | Latency/throughput across concurrency levels and context sizes |
| `spec_` | `tool-eval-bench --spec-bench` | Markdown | Speculative decoding quality (acceptance rate, speedup, efficiency) |
| `tool_` | `tool-eval-bench --perf` | Markdown | Tool-use performance benchmarks |

### Runtimes Supported

- **vLLM** — Primary runtime. Uses `modelopt` quantization, `flashinfer` attention backend, MTP/DFlash speculative decoding.
- **llama.cpp** — Via `llama-server`, uses GGUF models (Q8_0, Q4_K_S, etc.)
- **SGLang** — Mentioned in benchmarks but fewer recipes
- **atlas** — NVIDIA Atlas runtime (few recipes)

### Quantization Formats

- **NVFP4** — NVIDIA FP4 quantization (primary for DGX Spark)
- **FP8** — FP8 quantization
- **Q8_0** — GGUF Q8_0 (for llama.cpp)
- **Q4_K_S** — GGUF Q4_K_S (for llama.cpp)
- **INT4** — Autoround INT4
- **BF16** — Baseline, unquantized

## Key Files

| File | Purpose |
|------|---------|
| `.sparkrun/registry.yaml` | Registry metadata — name (`iromu`), recipe path, visibility |
| `bench.sh` | Benchmark runner script — runs spec-bench, perf-bench, and llama-benchy against a live endpoint |
| `check-vllm-health.sh` | Cron-based vLLM health monitor — probes `/health` or `/v1/models`, auto-restarts on failure with 10-min cooldown |
| `data/benchmarks.sqlite` | Local SQLite database storing benchmark results |
| `README.md` | Public-facing docs — how to add/run recipes via sparkrun CLI |

## Conventions & Practices

1. **Model directory naming**: kebab-case model slug (e.g., `qwen3.6-35b-a3b`, `qwen3.5-122b-a10b`)
2. **Recipe naming**: `<model-slug>-<quant>-<feature>-<backend>.sh/.yaml` (e.g., `qwen3.6-35b-a3b-nvfp4-mtp-vllm`)
3. **Benchmark naming**: `<type>_<recipe-name>.<ext>` matching the recipe slug
4. **Experimental recipes**: Go in `experimental/` directory, not yet promoted to `recipes/`
5. **Health monitoring**: `check-vllm-health.sh` is designed for crontab (every 1-2 min) with stateful cooldown
6. **No tests**: This is not a code project with unit tests — benchmarks *are* the verification
7. **No build step**: Recipes are declarative YAML + shell scripts — no compilation required

## How to Work With This Project

### Adding a New Recipe
1. Create a directory under `recipes/<model-slug>/`
2. Write the `.yaml` recipe definition (copy from a similar existing recipe as template)
3. Write the `.sh` launcher script (usually just `uvx sparkrun run <recipe-name>`)
4. Commit both files

### Running Benchmarks
1. Start the recipe: `cd recipes/<model>/<recipe> && uvx sparkrun run <recipe-name>`
2. Run `bench.sh` (edit MODEL_TAG and MODEL_PORT as needed)
3. Benchmark outputs land in `benchmarks/` as `benchy_*.json`, `spec_*.md`, `tool_*.md`

### Health Monitoring
- `check-vllm-health.sh` can be added to crontab for automatic vLLM restart
- State stored in `~/.local/share/vllm-health/restart.state`
- Logs written to `~/.local/share/vllm-health/vllm-health.log`

### Working with Experimental Recipes
- `experimental/` contains work-in-progress recipes not yet ready for general use
- Recipes here may use custom container images or experimental vLLM builds
- Once validated, promote to `recipes/`

## Important Notes

- This registry is for **personal use** on a DGX Spark device. Recipes are tuned for that specific hardware (GB10, sm_121a, 128GB unified memory).
- The `sparkrun` CLI (`uvx sparkrun`) is the primary interface — recipes are consumed via `sparkrun run`, `sparkrun list`, `sparkrun show`.
- Benchmark data is the source of truth for recipe quality — always check benchmarks before recommending a recipe.
