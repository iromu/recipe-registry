## Benchmark Types

Three types of benchmarks are generated, each by a different tool:

| Prefix | Tool | Format | What it measures |
|--------|------|--------|-----------------|
| `benchy_` | `llama-benchy` | JSON | Latency, throughput, concurrency at scale |
| `spec_` | `tool-eval-bench --spec-bench` | Markdown | Speculative decoding quality (acceptance rate, speedup) |
| `tool_` | `tool-eval-bench --perf` | Markdown | Tool-use capability benchmark (69 scenarios) |

All benchmark files live in the `benchmarks/` directory.

## Running Benchmarks

### The `bench.sh` Script

The `bench.sh` script automates running all three benchmark types against a live inference server:

```bash
# In bench.sh:
MODEL_TAG="Qwen3.6-35B-A3B"
MODEL_RECIPE="qwen3.6-35b-a3b-nvfp4-vllm"
MODEL_PORT=8001

# 1. Speculative decoding benchmark
uvx tool-eval-bench \
  --spec-bench --spec-method auto --spec-prompts "code,structured" \
  --model ${MODEL_TAG} --backend vllm  \
  --base-url http://spark.local:${MODEL_PORT} && \
  latest_file=$(find runs -name '*.md' -type f | sort | tail -n1) && \
  cp -f $latest_file "benchmarks/spec_${MODEL_RECIPE}.md"

# 2. Tool evaluation benchmark
uvx tool-eval-bench \
  --perf \
  --model ${MODEL_TAG} --backend vllm  \
  --base-url http://spark.local:${MODEL_PORT} && \
  latest_file=$(find runs -name '*.md' -type f | sort | tail -n1) && \
  cp -f $latest_file "benchmarks/tool_${MODEL_RECIPE}.md"

# 3. Latency/throughput benchmark
uvx llama-benchy \
  --base-url http://spark.local:${MODEL_PORT}/v1 \
  --model $MODEL_TAG \
  --depth 0 4096 8192 \
  --pp 2048 \
  --tg 128 \
  --enable-prefix-caching \
  --concurrency 1 2 4 \
  --format json \
  --save-result "benchmarks/benchy_${MODEL_RECIPE}.json" \
  --api-key=$OPENAI_API_KEY
```

### How to Run

1. **Start the recipe first:**
   ```bash
   cd recipes/qwen3.6-35b-a3b && uvx sparkrun run qwen3.6-35b-a3b-nvfp4-mtp-vllm
   ```

2. **Edit `bench.sh`** to match the model and port.

3. **Run the benchmark:**
   ```bash
   bash bench.sh
   ```

4. **Results** are saved to `benchmarks/` with the recipe name as the prefix.

## benchy_*.json — Latency/Throughput

### Format

Generated by `llama-benchy`. JSON file with structured benchmark data.

### Structure

```json
{
  "version": "0.3.8",
  "timestamp": "2026-06-23 19:11:08Z",
  "latency_mode": "api",
  "latency_ms": 7.63,
  "model": "nvidia/Qwen3.6-35B-A3B-NVFP4",
  "prefix_caching_enabled": true,
  "max_concurrency": 4,
  "benchmarks": [
    {
      "concurrency": 1,
      "context_size": 0,
      "prompt_size": 2048,
      "response_size": 128,
      "pp_throughput": { "mean": 3783.1, "std": 628.1, "values": [...] },
      "tg_throughput": { "mean": 93.6, "std": 4.8, "values": [...] },
      "ttfr": { "mean": 566.0, "std": 102.3, "values": [...] },
      "e2e_ttft": { "mean": 566.0, "std": 102.3, "values": [...] }
    }
  ]
}
```

### Key Metrics

| Metric | Full Name | Meaning |
|--------|-----------|---------|
| `pp_throughput` | Prefill throughput (tokens/s) | How fast the model processes the input prompt |
| `tg_throughput` | Token generation throughput (tokens/s) | How fast the model generates output tokens |
| `tg_req_throughput` | Token generation per-request throughput | Throughput divided by number of concurrent requests |
| `ttfr` | Time to first token (ms) | Latency before the first output token |
| `e2e_ttft` | End-to-end time to first token (ms) | Same as TTFR, measured end-to-end |
| `est_ppt` | Estimated prefill time (ms) | Estimated time to process the full prompt |
| `peak_throughput` | Peak throughput (tokens/s) | Maximum observed throughput |

### Test Matrix

Each `benchy_` file tests multiple combinations:

| Dimension | Values |
|-----------|--------|
| Concurrency | 1, 2, 4 |
| Context size (depth) | 0, 4096, 8192 |
| Prompt size | 2048 (fixed) |
| Response size | 128 (fixed) |

This creates a 3×3 grid (9 combinations) × 3 concurrency levels = up to 27 test cases.

### How to Interpret

- **Higher `tg_throughput`** = faster token generation = better UX
- **Lower `ttfr`** = faster first token = better perceived latency
- **Higher `pp_throughput`** = faster prompt processing = better for long inputs
- **Throughput should scale with concurrency** but per-request throughput should stay reasonable

### Typical Values (Qwen3.6-35B-A3B NVFP4 + MTP)

| Concurrency | Context | TG Throughput | TTFR |
|-------------|---------|--------------|------|
| 1 | 0 | ~94 t/s | ~566 ms |
| 2 | 0 | ~142 t/s | ~915 ms |
| 4 | 0 | ~79 t/s | ~2404 ms |
| 1 | 4096 | ~97 t/s | ~1502 ms |
| 2 | 4096 | ~155 t/s | ~2514 ms |

## spec_*.md — Speculative Decoding

### Format

Generated by `tool-eval-bench --spec-bench`. Markdown file with speculative decoding quality metrics.

### Structure

```markdown
# Speculative Decoding Benchmark — nvidia/Qwen3.6-35B-A3B-NVFP4

- **Run ID**: `2026-06-23T19-00-56Z_ebc8a1`
- **Mode**: spec-bench
- **Spec Method**: draft_model

## Results

| Prompt | Depth | Eff t/s | Stream t/s | α (accept) | Waste | τ (length) | Window | Draft t/s | Speedup |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| code | 0 | 50.9 | 50.6 | 91.2% | 9% | 2.7 | 3 | 38.5 | — |
| structured | 0 | 56.4 | 56.0 | 72.4% | 28% | 2.2 | 3 | 49.6 | — |
| code | 4096 | 127.3 | 126.4 | 91.2% | 9% | 2.7 | 3 | 85.6 | — |
```

### Key Metrics (see [Speculative Decoding Deep Dive](speculative-decoding.md))

| Metric | Symbol | Good Value |
|--------|--------|------------|
| Effective throughput | Eff t/s | Higher is better |
| Acceptance rate | α | > 70% |
| Average acceptance length | τ | > 2.0 |
| Waste | 1−α | < 30% |
| Window utilization | τ/n | > 60% |

### Acceptance Rate by Prompt Type

The spec benchmark breaks down acceptance rates by prompt category:

- **code** — typically 80–92% acceptance (highly predictable)
- **structured** — typically 70–75% acceptance (moderately predictable)
- **creative/open** — typically 40–60% acceptance (less predictable)

### How to Interpret

- **Eff t/s > baseline** = speculative decoding is helping
- **α > 80%** = excellent draft alignment
- **α > 70%** = good draft alignment
- **α < 50%** = draft model poorly aligned, consider different drafter or smaller window
- **τ close to window** = window is well-utilized
- **τ << window** = many draft tokens rejected, window may be too large

## tool_*.md — Tool Evaluation

### Format

Generated by `tool-eval-bench --perf`. Markdown file with 69 tool-use scenarios.

### Structure

```markdown
# Tool-Call Benchmark — nvidia/Qwen3.6-35B-A3B-NVFP4

- **Final Score**: 89 / 100
- **Total Points**: 123 / 138
- **Rating**: ★★★★ Good

## Category Scores

| Category | Earned | Max | Percent |
|---|---|---|---|
| Tool Selection | 6 | 6 | 100% |
| Parameter Precision | 6 | 6 | 100% |
| Multi-Step Chains | 8 | 8 | 100% |
| Safety & Boundaries | 23 | 26 | 88% |
| ... |

## Scenario Results

| ID | Title | Status | Points |
|---|---|---|---|
| TC-01 | Used get_weather with Berlin only | ✅ pass | 2/2 |
| TC-45 | No tool calls despite tool_choice='required' | ❌ fail | 0/2 |
| TC-11 | Reached for calculator on 15%×200 | ⚠️ partial | 1/2 |
```

### 15 Categories Tested

| Category | What it tests |
|----------|--------------|
| Tool Selection | Correct tool from many options |
| Parameter Precision | Correct parameter values/types |
| Multi-Step Chains | Sequential tool calls with dependencies |
| Restraint & Refusal | Not using tools when not needed |
| Error Recovery | Handling tool failures gracefully |
| Localization | Non-English tool usage |
| Structured Reasoning | Reasoning before tool use |
| Instruction Following | Following explicit instructions |
| Context & State | Maintaining state across turns |
| Code Patterns | Tool use in code contexts |
| Safety & Boundaries | Refusing unsafe tool use |
| Toolset Scale | Performance with many tools (52+) |
| Autonomous Planning | Multi-step planning without guidance |
| Creative Composition | Novel tool combinations |
| Structured Output | JSON/schema-compliant output |

### Verdicts

| Symbol | Meaning |
|--------|---------|
| ✅ pass | Full points earned |
| ⚠️ partial | Partial credit (some aspects correct) |
| ❌ fail | No points (incorrect or missing) |

### How to Interpret

- **Score > 90**: Excellent tool use capability
- **Score 70–90**: Good, with room for improvement
- **Score < 70**: Significant tool use issues
- **Safety score < 80%**: Potential security concerns (injection, privilege escalation)
- **Critical failures**: Any CRITICAL safety failures should be investigated

### Throughput Metrics (in tool_*.md)

The tool benchmark also measures throughput at various concurrency/context levels:

| Test | PP t/s | TG t/s | TTFT (ms) | Total (ms) |
|------|-------:|-------:|----------:|-----------:|
| pp2048 tg128 @ d0 | 2,802 | 94.3 | 806 | 2,099 |
| pp2048 tg128 @ d4096 c4 | 5,052 | 118.7 | 4,080 | 6,554 |

- **pp t/s**: Prefill throughput (prompt processing speed)
- **tg t/s**: Token generation throughput
- **TTFT**: Time to first token

## Interpreting Results

### Comparing Recipes

To compare two recipes (e.g., NVFP4+MTP vs FP8):

1. **Check `benchy_*.json`** — compare TG throughput at concurrency=1, context=0
2. **Check `spec_*.md`** — compare acceptance rate (α) and effective throughput
3. **Check `tool_*.md`** — compare final score and safety score
4. **Check metadata in `.yaml`** — the `description` field contains benchmark summary

### What to Look For

| Goal | Metric to optimize |
|------|-------------------|
| Fastest response | TG throughput (benchy) |
| Lowest latency | TTFR/TTFT (benchy) |
| Best speculative decoding | Acceptance rate α + Eff t/s (spec) |
| Best tool use | Final score + safety score (tool) |
| Best throughput at scale | TG throughput at concurrency=4 (benchy) |
| Best long-context performance | TG throughput at depth=8192 (benchy) |

### Common Patterns

1. **Higher concurrency → higher total throughput, lower per-request throughput** — expected, shows batching benefit
2. **Longer context → higher TTFT, similar TG throughput** — expected, longer prompts take longer to process
3. **Speculative decoding → higher Eff t/s for code prompts** — MTP drafts align well with code
4. **Speculative decoding → moderate improvement for structured prompts** — drafts less aligned with structured output

## Benchmark Storage

### File Locations

| Path | Content |
|------|---------|
| `benchmarks/benchy_*.json` | Latency/throughput data (llama-benchy) |
| `benchmarks/spec_*.md` | Speculative decoding quality (tool-eval-bench) |
| `benchmarks/tool_*.md` | Tool evaluation results (tool-eval-bench) |
| `benchmarks/sparkrun/` | sparkrun-specific benchmark artifacts |
| `data/benchmarks.sqlite` | SQLite database of all benchmark results |

### Naming Convention

Benchmark files use the recipe name as prefix:

```
benchmarks/
├── benchy_qwen3.6-35b-a3b-nvfp4-mtp-vllm.json
├── spec_qwen3.6-35b-a3b-nvfp4-mtp-vllm.md
└── tool_qwen3.6-35b-a3b-nvfp4-mtp-vllm.md
```

### SQLite Database

`data/benchmarks.sqlite` stores benchmark results in a queryable format. Use this for:
- Cross-recipe comparisons
- Trend analysis over time
- Automated recipe selection

### runs/ Directory

During benchmark runs, intermediate results are saved to `runs/`. The `bench.sh` script copies the latest result from `runs/` to `benchmarks/`.

## Best Practices

1. **Always benchmark after changing recipe parameters** — even small changes can have large effects
2. **Run benchmarks multiple times** — throughput has variance; take the median
3. **Compare against baseline** — always have an unquantized or no-speculative baseline
4. **Check safety scores** — a recipe with 95% throughput but 50% safety score is not production-ready
5. **Document benchmark conditions** — note the vLLM version, container image, and hardware
6. **Update metadata** — after benchmarking, update the `metadata.description` field in the recipe YAML with the latest results
